# 記事用素材

## 気づき

### 1. AIに実行承認しても、実行先が正しいとは限らない

- Codexに1コマンドだけを承認した。
- しかし、Codexの実行ツールが対象のテストPCに接続していることを証明できなかった。
- Codexはコマンドを実行せず停止した。
- 最終的にはユーザー本人が、対象PCを確認して手動実行する方法を採用した。

**学び：実行承認、実行対象、実行権限は別々に確認する必要がある。**

AIへの指示が明確でも、実行環境の紐づけが曖昧なら安全とは言えない。

### 2. 読取り専用スクリプトでも安全範囲を逸脱し得る

- ACL取得スクリプトには設定変更処理がなかった。
- しかし、ローカルユーザー・グループの全件照会が含まれていた。
- パス検査より先に対象へアクセスする順序上の懸念もあった。
- 入力した実パスが画面上に残るリスクも確認された。

**学び：「変更しない」と「許可した情報しか読まない」は別の要件。**

Read-onlyという表現だけでは、アクセス範囲と情報開示範囲を十分に定義できない。

### 3. Windows標準GUIと最小コマンドで十分な場合がある

- 当初はPowerShell調査を準備した。
- 静的レビューで問題点が見つかった。
- ACLの主要情報はWindowsのセキュリティ詳細設定で確認できた。
- 不足したグループ所属情報は、限定したWindows標準コマンド1回で補えた。

**学び：調査の目的に対して、最も小さい手段を選ぶことが重要。**

新しいスクリプトを書くことが、必ずしも最善の解決策ではない。

### 4. ACL一覧にUsersが存在しなくても安全とは断定できない

- ルートACL一覧には4つのACEが存在した。
- Users、Authenticated Users、EveryoneのACEは存在しなかった。
- しかし、他グループ経由の許可や子要素の個別ACLは未確認だった。
- 専用ユーザーのアクセス不可は証明できなかった。

**学び：ACLの棚卸しと実効アクセス検証を分ける必要がある。**

一覧上のACE不在と、実際のアクセス拒否は同義ではない。

### 5. 「調査完了」と「安全性確認完了」は異なる

- F1-READ-01は`COMPLETE_WITH_LIMITATIONS`で終了。
- しかし、C1のアクセス隔離は`NOT_VERIFIED`を維持。
- F1-2の設計レビューもOpen Conditions付きで終了した。
- 環境構築やPreflightへ自動的に移行しなかった。

**学び：工程の完了判定は、その工程で定義した責務に限定する。**

未解決事項を残していても、正しく管理されていれば調査工程は終了できる。

### 6. ソフトウェアの存在と利用可能性は違う

- Excelが現在のユーザーで動作していても、別ユーザーでの動作は未保証。
- VBE DLLが存在しても、VBE操作やCompileの成功は未保証。
- Officeライセンスの利用条件と実際の認証状態も別。
- Office 2019のサポート終了と、直ちに利用不能であることも別。

**学び：インストール、ライセンス、実行可能性、安全性を独立した確認項目にする。**

### 7. AIとの開発ではUNKNOWNを残す勇気が必要

- Codexの出力やユーザーの手動確認を、独立検証済みの結果に変換しなかった。
- Windowsグループのメンバー名から主体区分を推定しなかった。
- P01と同名ローカルグループのSID一致を推測しなかった。
- Excelの既存動作実績を専用ユーザーへ転用しなかった。

**学び：UNKNOWNを減らすことだけを目的にすると、不要な調査や過剰な操作が増える。**

必要なUNKNOWNを残したまま、次工程へ正確に引き継ぐほうが合理的な場合もある。

## 記事にできそうな切り口

### 開発日記向き

#### 1. 「AIに1行のコマンドを任せるだけなのに、なぜここまで確認したのか」

- 最初はグループのメンバーを調べたいだけだった。
- AI側の実行先が確認できず停止した。
- 実行方法をユーザー手動へ変更。
- 証拠の区分と承認範囲まで整備した。
- 個人開発におけるAI実行権限のリアルな課題。

#### 2. 「PowerShellスクリプトを作ったのに、結局使わなかった話」

- ACL調査のためスクリプトを準備。
- 静的レビューで読取り範囲とパス検査の問題を発見。
- GUIと既存コマンドで調査を代替。
- 作ったものを無理に使わない判断。

記事の中心メッセージ：**手段を完成させることより、目的を安全に達成することが重要。**

#### 3. 「Windows 11 HomeでAI開発用の隔離環境を作ろうとしたら」

- 自宅のWindows 11 Homeを検証PCとして利用。
- 専用標準ユーザー方式を検討。
- CodexSandboxUsersの存在を確認。
- Office 2019の利用条件も問題になった。
- Homeエディションと個人所有PCによる検証環境構築の制約。

#### 4. 「AIが勝手に作業を進めない開発プロセスを考える」

- 机上レビューと実行を分離。
- 承認した操作だけを実行。
- 対象PCが不明なら停止。
- 調査が完了しても後続工程へ勝手に進まない。
- 個人開発でも承認ゲートが有効だった事例。

#### 5. 「小さなツール開発で、なぜここまでEvidenceにこだわるのか」

- Excel VBAの定型メールツール開発から始まった。
- P2-05のCompile検証が環境安全性の検討につながった。
- 手動申告、静的レビュー、実機確認を区別。
- 開発の再現性と検証コストのバランスを考えた。

## 技術記事向き

### 1. Windows ACLの確認と実効アクセス評価の違い

内容候補：

- NTFS DACLとACE
- Allow／Deny
- Explicit／Inherited
- アクセストークンと所属グループ
- ルートACLと子要素ACL
- 共有経路とNTFS権限
- SID一致の必要性
- 実効アクセスを判断するための確認条件

タイトル案：

**「Windows ACLにUsersがなくても安全とは限らない理由」**

### 2. AIエージェント実行におけるAuthorizationとExecution Target Binding

内容候補：

- 実行承認の対象を限定する。
- 実行対象PCを確認する。
- 非昇格と標準ユーザーを区別する。
- 実行回数を限定する。
- 失敗時のSTOP条件を設定する。
- エージェントの実行環境が不明な場合にどう扱うか。

タイトル案：

**「AIにコマンド実行を許可する前に確認すべき5つの条件」**

### 3. Read-onlyスクリプトのセキュリティレビュー

内容候補：

- 読取り専用と非変更の違い
- アクセス対象を限定する設計
- ローカルアカウント列挙の取り扱い
- ReparsePoint検査順序
- 画面出力・実パスの漏えい
- 静的レビューと実機検証の分離
- 最小権限と最小情報取得

タイトル案：

**「Read-onlyだから安全、ではない：ACL調査スクリプトのレビュー実例」**

### 4. VBA Compile用の隔離環境設計

内容候補：

- 既存Excelプロセスと検証用環境の分離
- Windows専用ユーザー
- Officeライセンス・認証条件
- Excel／VBE／Compileの利用可能性
- マクロ・イベント・起動時追加物のリスク
- 無害Fixtureを用いたPreflight
- Production Workbookに進む前のGate設計
- Fixture PASSとProduction Compile PASSの区別

タイトル案：

**「Excel VBAを安全にCompileするための検証環境を設計する」**

今回の会話では設計レビューまでであり、隔離環境の構築や安全なCompileの実証は未完了であることを明記する。

### 5. AI協働開発におけるEvidenceの品質管理

内容候補：

- `USER_ATTESTED`
- `USER_MANUAL_GUI`
- `USER_MANUAL_COMMAND`
- `CODEX_OBSERVED`
- `NOT_VERIFIED`
- `COMPLETE_WITH_LIMITATIONS`
- `REVIEW_REQUIRED`

タイトル案：

**「AIとの開発で『確認済み』を安易に使わないためのEvidence設計」**

### 6. 完了判定と承認ゲートの設計

内容候補：

- タスク終了条件の定義
- Open Conditions付き完了
- 調査完了と隔離成立の分離
- 設計レビュー完了と実行許可の分離
- 変更操作の承認
- 後続工程へのUNKNOWN引継ぎ
- Baseline／Decision Log／Project Controlの役割分離

タイトル案：

**「DONEでも安全とは限らない：AI協働開発のゲート設計」**
