# 2. 企画概要

本企画では、Outlookのメールテンプレートファイル（`.oft`）内に記述された変数をExcelから入力し、任意の値へ置換したうえで、送信用メールを自動生成するツールを開発する。

メールテンプレート内では、以下の形式で変数を記述する。

```text
{{VariableName}}
```

例：

```text
件名：
【{{ModelName}}】ゲート審査のご案内

本文：
{{PIC}} 様

{{GateDate}} にゲート審査を実施します。
```

ツールはテンプレート内の変数を自動検出し、Excel上に保持された変数定義情報と同期する。

各変数には、

- 文字列
- 数値
- 日付
- 単一選択
- 複数選択
- URL

などの型を設定できるようにし、その設定に応じた入力UIをUserForm上に生成する。

入力された値を検証・整形したうえでSubjectおよびBodyの変数を置換し、Classic Outlook上にメールを表示する。

ツール自身による自動送信は行わず、最終的な送信判断はユーザーが行う。

---

# 3. 背景

定型メール業務では、既存メールやテンプレートをコピーして使用する運用が多く、以下のような問題が発生しやすい。

- 日付や担当者名などの変更漏れ
- 前回メールの情報が残る
- 手入力による誤記
- テンプレートごとに入力項目が異なる
- 同種メールでも作成方法が属人化する
- メール本文や件名の修正箇所をユーザーが把握する必要がある
- テンプレート変更後にExcel側設定との不整合が発生する可能性がある

これらを解決するため、

> **メール本文を直接編集するのではなく、必要な情報を入力し、テンプレートからメールを生成する方式**

へ変更する。

---

# 4. 目的

本ツールの目的は、定型メール作成における以下の改善を実現することである。

## 4.1 入力ミス・変更漏れの低減

ユーザーが変更対象箇所をメール本文から探すのではなく、必要項目だけを入力する方式とする。

---

## 4.2 メール作成作業の標準化

テンプレート、変数定義、入力UIを共通化し、ユーザーごとの作成方法の差を減らす。

---

## 4.3 テンプレート変更への追従性向上

メールテンプレートから変数を自動抽出し、既存の設定情報と同期することで、テンプレート変更時の設定修正負荷を低減する。

---

## 4.4 再利用可能なメール生成基盤の構築

特定メール専用のVBAを作るのではなく、テンプレートと設定を変更することで複数用途へ展開可能な構造とする。

---

# 5. 企画コンセプト

本ツールは単なるExcelメール送信マクロではなく、

> **設定駆動型の定型メール生成ツール**

として設計する。

基本構造は以下とする。

```text
Outlook Template (.oft)
        │
        ├─ Subject
        └─ Body
             │
             ▼
       Variable Scan
             │
             ▼
     Variable Definition
             │
             ▼
      UserForm Generator
             │
             ▼
        User Input
             │
             ▼
        Validation
             │
             ▼
       Render / Replace
             │
             ▼
     Outlook Mail Display
```

# 6. 基本設計方針

## 6.1 テンプレートと設定を分離する

メールテンプレートには、原則として表示内容と変数のみを保持する。

例：

```text
{{GateDate}}
```

以下のような型やロジックはテンプレート側へ埋め込まない。

```text
{{GateDate:Date:yyyy/mm/dd}}
```

型、表示形式、必須条件、選択肢などはExcel側のVariableDefinitionで管理する。

---

## 6.2 変数記法

変数は以下の形式に統一する。

```text
{{VariableName}}
```

同一変数がSubjectまたはBody内に複数回存在した場合も、変数定義としては1件として扱う。

---

## 6.3 対象範囲

変数置換対象は以下とする。

- Subject
- Body

MVPではTo、CC、BCCは対象外とする。

---

# 7. 変数定義

変数ごとに、Excel上で以下の情報を保持する。

| 項目 | 内容 |
|---|---|
| VariableName | テンプレート内の変数名 |
| DisplayName | UserFormに表示する名称 |
| Type | 変数型 |
| Required | 必須入力か |
| DefaultValue | 初期値 |
| Format | 日付・数値等の出力書式 |
| OptionSource | 選択肢の参照元 |
| SortOrder | UserForm表示順 |
| Description | 入力説明 |
| TemplateLocation | Subject / Body / Both |
| Status | Active / Unused |
| FirstDetectedAt | 初回検出日時 |
| LastDetectedAt | 最終検出日時 |

---

# 8. 変数型

最終的に以下の型をサポート対象とする。

| Type | 用途 |
|---|---|
| Text | 一般文字列 |
| Number | 数値 |
| Date | 日付 |
| Select | 単一選択 |
| MultiSelect | 複数選択 |
| URL | URL文字列 |

型に応じてUserForm上の入力コントロールを変更する。

例：

| Type | UI |
|---|---|
| Text | TextBox |
| Number | TextBox + 数値検証 |
| Date | 日付入力 |
| Select | ComboBox |
| MultiSelect | ListBox |
| URL | TextBox + URL検証 |

---

# 9. テンプレート同期機能

## 9.1 基本方針

テンプレート変更時にVariableDefinitionを再生成するのではなく、

> **既存設定を保持した差分同期**

を行う。

---

## 9.2 同期処理

テンプレートから抽出した変数と既存VariableDefinitionを比較し、以下の処理を行う。

### 新規変数

テンプレートに存在し、VariableDefinitionに存在しない場合：

```text
New → VariableDefinitionへ追加
```

初期設定例：

```text
Type         = Text
Required     = False
Status       = Active
DisplayName  = VariableName
```

---

### 継続変数

テンプレートにもVariableDefinitionにも存在する場合：

```text
Existing → 既存設定を保持
```

ユーザーが設定したType、DisplayName、OptionSourceなどは変更しない。

---

### 削除された変数

VariableDefinitionには存在するがテンプレートには存在しない場合：

```text
Missing → Status = Unused
```

設定行自体は削除しない。

これにより、後からテンプレートへ変数が復活した場合に既存設定を再利用できる。

---

## 9.3 変数名変更

以下の変更：

```text
{{PIC}}
```

↓

```text
{{PersonInCharge}}
```

はシステム上、自動的なRenameとは判定しない。

以下として扱う。

```text
PIC             → Unused
PersonInCharge  → New
```

変数名変更を自動推測しないことで、誤った設定引継ぎを防止する。

---

```text
未使用
- Department
```

テンプレート変更による影響をユーザーが確認できる構造とする。

# 11. UserForm

VariableDefinitionを基に入力画面を動的生成する。

例：

```text
┌──────────────────────────────┐
│ 定型メール作成               │
│                              │
│ 機種名                       │
│ [________________________]   │
│                              │
│ 審査日                       │
│ [2026/09/10_____________]    │
│                              │
│ 部署                         │
│ [設計部_______________▼]    │
│                              │
│ 関係部署                     │
│ [ ] 設計部                   │
│ [ ] 品質部                   │
│ [ ] 生産部                   │
│                              │
│        [メール作成]          │
└──────────────────────────────┘
```

UserFormそのものをテンプレートごとに個別開発するのではなく、VariableDefinitionから生成する方式を基本とする。

---

# 12. MultiSelect

複数選択型では、選択された値をメール本文へどのように出力するか設定可能とする。

例：

選択値：

```text
設計部
品質部
生産部
```

出力例1：

```text
設計部、品質部、生産部
```

出力例2：

```text
設計部
品質部
生産部
```

必要に応じて、VariableDefinitionへ出力区切り設定を追加する。

---

# 13. URLおよびハイパーリンク

URL型では、通常文字列としてのURL置換に加え、メール本文内のハイパーリンク先を書き換える方式を検討する。

例：

```html
<a href="{{DocumentURL}}">資料はこちら</a>
```

この場合、画面表示文字列は固定したまま、リンク先のみ入力値へ変更できる。

URL文字列と通常文字列ではHTML上の扱いが異なるため、置換時には出力コンテキストを考慮する。

---

# 14. 入力検証

メール生成前に以下を確認する。

- 必須項目入力
- Number型の数値確認
- Date型の日付確認
- Select型の選択確認
- MultiSelect型の選択確認
- URL型のURL形式確認

入力エラーがある場合はメール生成を中止し、対象項目をユーザーへ通知する。

---

# 15. 未置換変数チェック

メール生成後、SubjectおよびBodyに以下の形式が残っていないことを確認する。

```text
{{Variable}}
```

残存していた場合はメールを表示せず、エラーとする。

例：

```text
メールを生成できません。

未置換変数：
・{{GateDate}}
・{{PIC}}
```

---

# 16. メール生成

入力値の検証完了後、OFTテンプレートを読み込み、SubjectおよびBodyの変数を置換する。

処理イメージ：

```text
User Input
    ↓
Validation
    ↓
Format
    ↓
HTML Encode等
    ↓
Variable Replace
    ↓
Remaining Variable Check
    ↓
Outlook Mail Display
```

---

# 17. メール送信方針

ツールによる自動送信は行わない。

メール生成後はClassic Outlook上にメールを表示し、ユーザーが以下を確認した後に手動で送信する。

- 宛先
- 件名
- 本文
- 入力内容
- 表示崩れ
- その他内容

基本動作：

```text
Excel
 ↓
メール生成
 ↓
Outlook Display
 ↓
ユーザー確認
 ↓
ユーザーがSend
```

# 21. 明示的な対象外

本ツールでは以下を実装対象外とする。

## 条件分岐

以下のようなテンプレートロジックは実装しない。

```text
{{#if XXX}}

{{else}}

{{/if}}
```

理由：

- テンプレート言語化を避ける
- 複雑性を抑える
- 保守性を維持する
- ユーザーが理解できる仕組みに限定する

---

## 添付ファイル自動処理

添付ファイルの自動追加は行わない。

理由：

- ファイルパス管理
- バージョン管理
- 権限制御
- ファイル存在確認
- クラウドストレージ連携

など、メール生成とは異なる責任が追加されるため。

---

## 自動送信

Outlookメールの自動送信は行わない。

最終確認および送信はユーザー責任とする。

# 25. 成功条件

本企画が成功したと判断する主な条件は以下とする。

1. ユーザーがメール本文を直接編集せずに定型メールを作成できる
2. テンプレートから変数を自動抽出できる
3. テンプレート変更後も既存変数設定を保持できる
4. 入力値の型および必須条件を検証できる
5. 未置換変数を残した状態でメールを生成しない
6. Outlook上で最終確認可能なメールを生成できる
7. テンプレート固有VBAを大量に追加せず、設定変更による横展開が可能である

# 26. 現時点の主要リスク

## R1. HTMLメールの置換

BodyがHTML形式の場合、通常文字列、改行、URLなどでエンコード方法が異なる。

対策：

- 型だけでなく出力コンテキストを考慮する
- HTMLBodyを扱う場合の置換ルールを設計する

---

## R2. UserForm動的生成の複雑化

型や項目数が増えると、UserFormレイアウト制御が複雑化する可能性がある。

対策：

- MVPではUIルールを固定する
- 自由配置は許可しない
- SortOrderを基準に縦並びとする

---

## R3. テンプレート変更による設定不整合

変数名変更を自動Renameと誤判定すると、異なる変数へ設定を引き継ぐ危険がある。

対策：

- Rename自動推測は行わない
- New / Existing / Unusedのみで同期する

---

## R4. 機能追加による肥大化

条件分岐、添付、自動送信などを追加すると、本来の目的から外れて複雑化する。

対策：

- 明示的な対象外機能を維持する
- 新機能追加時は企画目的との整合性を確認する
